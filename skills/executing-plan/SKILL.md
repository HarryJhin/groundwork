# executing-plan

플랜을 읽고, 비판적으로 검토하고, 전 태스크를 실행하고, 끝나면 보고한다.

## 입력

실행할 플랜 파일의 경로를 호출자에게 받는다. `groundwork:writing-plans`가 승인된 플랜을 넘길 때 그 경로를 함께 넘긴다. 경로를 받지 못했으면 어느 플랜을 실행할지 사용자에게 묻는다. 임의로 찾아 고르지 않는다.

## 출력

전 태스크를 마치면 사용자에게 보고한다. 무엇을 구현했는지, 어느 검증이 통과했는지, 플랜과 달라진 지점이 있으면 그것을 담는다. 그 뒤 통합 결정은 3단계가 `groundwork:finish`로 넘긴다.

**적용 판단**: 서브에이전트를 쓸 수 있는 에이전트 실행 환경에서는 `groundwork:subagent-driven-development`가 기본이다. 그쪽이 태스크마다 컨텍스트를 격리하고 리뷰 게이트를 건다. 이 스킬은 서브에이전트를 쓸 수 없거나 플랜이 작아 격리 이득이 없을 때 쓴다.

## 절차

### 1단계. 플랜을 읽고 검토한다

1. 격리된 워크스페이스를 확보한다. `groundwork:using-git-worktrees`로 만들거나 기존 것을 확인한다
2. 플랜 파일을 읽는다
3. 비판적으로 검토한다. 플랜에 대한 의문·우려를 식별한다
4. 우려가 있으면 시작 전에 사용자에게 제기한다
5. 우려가 없으면 태스크마다 todo를 만들고 진행한다

플랜을 한 번 훑어 충돌을 찾는다. 찾을 것은 이렇다.

- 태스크끼리 모순된다
- 태스크가 플랜 문서의 `Global Constraints` 절(플랜 전체에 걸리는 제약을 스펙에서 그대로 옮겨 적은 절)과 모순된다
- 플랜이 요구하는 구현을 코드 리뷰 기준(`groundwork:requesting-code-review`가 리뷰어에게 주입하는 프롬프트)이 결함으로 본다

찾은 것을 한 번에 묶어 사용자에게 제시하고 어느 쪽이 우선인지 묻는다.

### 2단계. 태스크를 실행한다

태스크마다 이렇게 한다.

1. in_progress로 표시한다
2. 각 단계를 정확히 따른다(플랜이 2~5분 단위 단계를 담고 있다)
3. 명세된 검증을 돌린다
4. completed로 표시한다

태스크 경계에서 작업 트리(체크아웃된 소스 전체)가 독립으로 빌드·테스트를 통과해야 한다. 통과하지 않으면 다음 태스크로 가지 않는다.

자동 테스트로 검증할 수 있는 태스크는 `groundwork:test-driven-development`를 따른다. 버그를 만나면 `groundwork:systematic-debugging`을 따른다. 완료를 주장하기 전에 `groundwork:verification-before-completion`을 따른다.

주요 태스크를 마쳤거나 머지에 가까워지면 `groundwork:requesting-code-review`로 리뷰어를 디스패치한다. 받은 피드백은 `groundwork:receiving-code-review`의 규율로 처리한다.

### 3단계. 개발을 마무리한다

전 태스크가 완료되고 검증되면 `groundwork:finish`를 쓴다. 그 스킬이 테스트를 확인하고 선택지를 제시하고 선택을 실행한다.

## 멈추고 물어야 할 때

**즉시 실행을 멈춘다**:
- 막힘을 만났다(빠진 의존성, 실패하는 테스트, 불명확한 지시)
- 플랜에 시작을 막는 결정적 공백이 있다
- 지시를 이해하지 못하겠다
- 검증이 반복해서 실패한다

추측하지 말고 설명을 요청한다.

## 앞 단계로 돌아가야 할 때

**1단계 검토로 돌아간다**:
- 사용자가 네 피드백으로 플랜을 갱신했다
- 근본 접근을 다시 생각해야 한다

막힘을 밀어붙이지 않는다. 멈추고 묻는다.

## 기억할 것

- 플랜을 먼저 비판적으로 검토한다
- 플랜 단계를 정확히 따른다
- 검증을 건너뛰지 않는다
- 플랜이 스킬을 지시하면 그 스킬을 참조한다
- 막히면 멈춘다. 추측하지 않는다
- 사용자의 명시 동의 없이 main·master 브랜치에서 구현을 시작하지 않는다
- 플랜에 없는 작업은 범위 변경이다. 사용자에게 확인한다
- 구현 중 스펙·플랜과 어긋난 사실을 발견하면 조용히 우회하지 않는다. 문서를 고치고 해당 리뷰어에게 재리뷰를 받는다
- 구현 중 스펙·플랜에 없던 판단은 보수적으로 택해 진행하고 기록한다. 그 repo의 아키텍처 결정이면 `groundwork:writing-adr`로 남긴다. 코드가 스스로 설명하는 세부는 코드 주석으로 둔다
