# writing-plans

승인된 스펙을 구현자가 그대로 실행할 수 있는 플랜으로 바꾼다. 플랜 승인이 마지막 사용자 게이트다. 여기를 지나면 구현·검증은 자율이다.

산출물은 `docs/plans/PLAN-NNNN-<topic>.md`다. 경로·명명·번호 규약 정본은 `groundwork:finding-unknowns`의 「산출물 규약」 절이다.

## 입력

승인된 스펙 파일의 경로를 호출자에게 받는다. `groundwork:finding-unknowns`가 스펙 승인 직후 이 스킬로 넘기면서 그 경로를 준다. 사용자가 직접 불러 경로가 없으면 어느 스펙의 플랜을 쓸지 묻는다. 스펙 없이 플랜을 시작하지 않는다. 번호 재사용과 `spec-alignment` 리뷰가 둘 다 스펙 경로에 의존한다.

## 독자 가정

**REQUIRED SUB-SKILL**: 플랜 본문을 쓰기 전에 `groundwork:writing-for-junior`(세션 맥락 없는 주니어 독자 기준의 작성 규범과 판정 렌즈)를 로드한다. 아래 독자 가정의 판정 기준과 작성 처방이 거기 있다. 리뷰의 `junior-read` 렌즈가 같은 기준으로 판정한다.

플랜을 읽을 구현자는 이 코드베이스 맥락이 없고 도메인을 모른다. 숙련된 개발자지만 우리 도구·문제 영역은 처음이고, 좋은 테스트 설계에도 밝지 않다고 가정한다. 그가 알아야 할 것을 전부 적는다. 어느 파일을 건드리는가, 무엇을 쓰는가, 어떻게 검증하는가.

이 가정은 실행 방식에서 온다. 태스크마다 fresh 구현자가 붙고, 그는 세션 히스토리를 상속받지 않는다. 플랜에 없는 것은 그에게 도달하지 않는다.

## 번호 재사용

플랜 파일의 4자리 번호와 `<topic>`은 대응 스펙 파일명에 이미 박힌 값을 그대로 복사한다. `<topic>`은 파일명 슬러그이고, 문서 h1의 `<제목>`은 사람이 읽는 명사구라 둘은 같은 값이 아니다. topic 문자열로 매칭하지 않고, 새 번호를 발급하지도 않는다. 스펙 `docs/specs/SPEC-0042-foo.md`의 플랜은 `docs/plans/PLAN-0042-foo.md`다.

## 범위 점검

스펙이 독립 서브시스템 여럿을 덮으면 스펙 단계에서 갈렸어야 한다. 갈리지 않은 채 넘어왔으면 서브시스템마다 별도 스펙·플랜으로 쪼갤 것을 제안한다. 플랜 하나는 그 자체로 동작하고 테스트되는 소프트웨어를 낳아야 한다.

대형 작업의 단계는 플랜 문서 내부의 단계로 표현한다. 플랜 파일을 쪼개지 않는다.

## 파일 구조

태스크를 정의하기 전에 어느 파일이 생기고 바뀌는지, 각 파일이 무엇을 책임지는지 먼저 그린다. 분해 결정이 여기서 확정된다.

- 경계가 뚜렷하고 인터페이스가 명확한 단위로 설계한다. 파일 하나가 책임 하나를 진다.
- 한 컨텍스트에 담기는 코드일수록 판단이 정확하고 편집이 안정된다. 너무 많은 일을 하는 큰 파일보다 초점이 좁은 작은 파일을 택한다.
- 함께 바뀌는 파일은 함께 둔다. 기술 계층이 아니라 책임으로 가른다.
- 기존 코드베이스에서는 확립된 패턴을 따른다. 코드베이스가 큰 파일을 쓴다면 독단으로 재구조화하지 않는다. 다만 수정 대상 파일이 이미 감당하기 어렵게 커졌다면 분할을 플랜에 넣어도 된다.

이 구조가 태스크 분해의 입력이다.

## 태스크 적정 크기

태스크는 자기 테스트 사이클을 지니고 fresh 리뷰어의 게이트를 받을 가치가 있는 최소 단위다. 경계를 그을 때는 셋업·설정·스캐폴딩·문서 작업을 그것이 필요한 산출물의 태스크 안으로 접어 넣는다. 리뷰어가 이웃 태스크를 승인하면서 이 태스크만 의미 있게 반려할 수 있는 지점에서만 가른다.

**태스크 경계 = 빌드·테스트 green**: 각 태스크가 끝난 시점에 트리가 독립으로 빌드·테스트를 통과해야 한다. 그 지점이 다음 fresh 구현자의 시작점이다. 중간이 green이 안 되는 강결합은 한 태스크로 합친다. 쪼개지지 않는다는 사실 자체가 병합 신호다.

## 태스크 안의 단계

각 단계는 행동 하나이고 2분에서 5분 규모다. 자동 테스트로 검증할 수 있는 태스크는 다음 단계를 체크박스로 담는다.

- [ ] 실패하는 테스트를 쓴다
- [ ] 실행해 실패를 확인한다
- [ ] 통과시킬 최소 구현을 쓴다
- [ ] 실행해 통과를 확인한다
- [ ] 커밋한다

## 플랜 문서 형식

### 헤더

```markdown
---
created: YYYY-MM-DD
---

# 플랜: <제목>

## Goal

<이 플랜이 무엇을 짓는지 한 문단> 대응 스펙: `docs/specs/SPEC-NNNN-<topic>.md`.

## Global Constraints (스펙 verbatim)

<스펙의 프로젝트 전역 요구를 정확한 값 그대로 한 줄씩. 버전 하한·의존 제한·명명·플랫폼 요구 등. 모든 태스크의 요구에 이 절이 암묵으로 포함되고, 실행 스킬이 태스크마다 구현자 서브에이전트에게 주는 지시문에 그대로 실린다.>
```

Global Constraints는 요약하지 않는다. 요약은 값을 잃고, 잃은 값은 구현자에게 도달하지 않는다.

### 태스크

````markdown
### Task N: <컴포넌트 이름>

- **Files**
  - 신규 `exact/path/to/file.py`: <함수·모듈 시그니처>
  - 변경 `exact/path/to/existing.py`: <심볼명>에 <추가|변경|삭제>
  - 삭제 `exact/path/to/gone.py`
- **Interfaces**
  - Consumes: <앞 태스크에서 쓰는 것, 정확한 시그니처>
  - Produces: <뒤 태스크가 의존하는 것, 정확한 함수명·파라미터·반환 타입>
- **단계**: 「태스크 안의 단계」의 체크박스 (자동 테스트로 검증할 수 있으면)
- **실행 검증**: <이 태스크의 산출물을 판정하는 커맨드>
- **의존**: <선행 태스크 번호, 없으면 "없음">
````

Files는 심볼마다 추가·변경·삭제 중 무엇인지 표시한다. 어떤 함수·API가 생기고 바뀌고 사라지는지가 플랜의 핵심 계약이다. 기존 파일은 심볼명으로 지정하고 라인 번호는 쓰지 않는다. 라인은 낡고 LSP는 심볼로 착지하므로 라인 병기가 오히려 조회 낭비를 부른다. 명명된 심볼이 없는 지점은 구조로 서술한다(예: 파일 상단 import 블록).

Interfaces의 Produces가 중요하다. 태스크 구현자는 자기 태스크만 본다. 이웃 태스크가 쓰는 이름과 타입을 그가 배우는 경로가 이 블록뿐이다.

실행 검증 커맨드는 그 태스크의 산출물을 실제로 판정해야 한다. 무엇을 해도 통과하는 커맨드는 검증이 아니다.

## placeholder 금지

모든 단계는 구현자가 필요로 하는 실제 내용을 담는다. 다음은 플랜 결함이므로 쓰지 않는다.

- "TBD", "TODO", "나중에 구현", "세부는 채워 넣기"
- "적절한 에러 처리 추가", "검증 추가", "엣지케이스 처리"
- 실제 테스트 코드 없는 "위 내용의 테스트 작성"
- "Task N과 유사"(코드를 반복한다. 구현자는 태스크를 순서대로 읽지 않을 수 있다)
- 무엇을 할지만 말하고 어떻게 할지 보이지 않는 단계
- 어느 태스크에서도 정의하지 않은 타입·함수·메서드 참조

## 리서치 경계

- 심볼·시그니처는 Read·LSP로 실측한다. 추정하지 않는다.
- 스펙이 결정한 기술의 세부는 공식 문서로 조회한다.
- 스펙에 없는 기술 선택·가정은 조사로 메우지 않는다. 스펙으로 회귀한다.

## 셀프 리뷰

플랜을 다 쓴 뒤 스펙을 새 눈으로 다시 보고 대조한다. 이것은 직접 도는 체크리스트이고 서브에이전트 디스패치가 아니다.

1. **스펙 커버리지**: 스펙의 각 절·요구를 훑으며 그것을 이행하는 태스크를 지목할 수 있는지 본다. 지목 실패는 공백이다.
2. **placeholder 스캔**: 「placeholder 금지」의 패턴을 플랜에서 찾는다.
3. **타입 정합**: 뒤 태스크에서 쓴 타입·시그니처·속성명이 앞 태스크가 정의한 것과 맞는지 본다. Task 3의 `clearLayers()`가 Task 7에서 `clearFullLayers()`가 됐다면 버그다.

찾은 문제는 그 자리에서 고친다. 재검토는 필요 없다. 스펙 요구에 대응 태스크가 없으면 태스크를 추가한다.

## 리뷰 패널

- in: 플랜 + 대응 스펙 경로 / out: 리뷰어 전원 PASS
- **REQUIRED SUB-SKILL**: `groundwork:plan-review`를 호출한다. 그 스킬이 로스터 선정·디스패치·재리뷰를 맡는다. 대응 스펙 경로를 함께 넘긴다(`spec-alignment`가 대조에 쓴다).

## 게재·승인 (마지막 사용자 게이트)

- in: 통과 플랜 / out: 사용자의 명시 승인
- 통과 플랜을 HTML 아티팩트로 게재해 첨삭·승인을 받는다. 게재 전에 `artifact-design`(아티팩트 페이지 설계 규범. groundwork가 아니라 에이전트 실행 환경이 제공하는 스킬이다)을 로드한다. 그 스킬이 없는 실행 환경이면 플랜 경로를 그대로 제시하고 승인을 받는다.
- 승인은 명시 승인 발화로만 확정한다. 침묵·모호 발화는 승인이 아니다. 게재 후 발화가 승인도 첨삭도 아니면 즉시 AskUserQuestion으로 묻는다.
- 첨삭은 개정 → 재리뷰 → 동일 URL 재게시로 반영한다.
- 게재물은 원문 복사가 아니라 승인자를 위한 검토용 요약이다. 승인이 필요한 결정·트레이드오프·범위·리스크 중심으로 재구성하고 원문 경로를 명시한다.

## 핸드오프

승인 후 실행 스킬로 넘긴다. 서브에이전트를 쓸 수 있으면 `groundwork:subagent-driven-development`가 기본이다(태스크마다 fresh 구현자 + 리뷰 게이트). 서브에이전트를 쓸 수 없거나 플랜이 작아 격리 이득이 없으면 `groundwork:executing-plan`으로 인라인 실행한다. 어느 쪽이든 종료는 `groundwork:finish`가 맡는다.

## Rules

- 플랜은 스펙 결정을 재검토하는 자리가 아니다. 스펙과 어긋난 사실을 발견하면 조용히 우회하지 말고 스펙으로 회귀해 개정·재리뷰한다.
- 스펙 내용의 요약 재서술을 플랜에 넣지 않는다. Global Constraints의 verbatim 복사만 예외다.
- 수용 기준(Acceptance Criteria) 대조표를 따로 두지 않는다. 검증은 태스크의 실행 검증 커맨드로만 표현한다.
- 결정 이유의 서사는 플랜에 담지 않는다. 그 repo의 아키텍처 결정이면 `groundwork:writing-adr`로 남긴다.
