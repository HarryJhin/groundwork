# Choose a model tier

서브에이전트를 디스패치하거나 세션을 나눌 때 어느 모델로 돌릴지 정하는 규율이다.
groundwork에서 모델을 고르는 스킬이 모두 이 문서를 기준으로 쓴다.

**주체**는 모델을 고르는 에이전트다.
디스패치되는 서브에이전트는 이 문서를 읽지 않는다.

**소유**는 `groundwork:using-groundwork`(부트스트랩)다.
모델 티어는 설계·리뷰·실행 어느 단계에도 걸리는 교차 규범이라 특정 실행 경로가 소유하지 않는다.

**경로 기준**은 플러그인 루트다.
다른 문서가 이 파일을 가리킬 때 쓰는 경로는 `${CLAUDE_PLUGIN_ROOT}/skills/using-groundwork/choosing-model-tier.md`이고 `${CLAUDE_PLUGIN_ROOT}`는 groundwork 플러그인이 설치된 디렉터리이지 실행 시점 작업 디렉터리가 아니다.

## Tiers

티어는 실행 환경이 제공하는 모델을 능력 순으로 늘어놓은 층이다.
이 문서는 그것을 3개 층으로 나눠 쓰고 각 층에 어느 모델이 드는지는 실행 환경마다 다르다.

- **싼 모델**: 가장 빠르고 싼 층
- **표준 모델**: 중간 층
- **가장 유능한 모델**: 최상위 층

모델 이름을 이 문서에 적지 않는 이유는 두 가지다.
모델은 이 문서보다 빨리 바뀐다.
그리고 groundwork는 실행 환경을 가리지 않으므로 어느 실행 환경에서도 층 이름이 해소돼야 한다.

## Explicit model is mandatory

**서브에이전트를 디스패치할 때 모델을 항상 명시한다.**
모델을 빠뜨리면 세션 모델을 상속하고 그것은 대개 가장 유능하고 가장 비싼 모델이라 이 문서가 무력해진다.
실행 환경의 디스패치 도구가 제공하는 모델 파라미터를 쓴다.

reasoning effort는 이 규율에 넣지 않는다.
실행 환경에 따라 디스패치 시점에 지정하는 수단이 없고 세션 값을 상속한다.

## The two axes of assignment

모델을 고르는 자리는 둘이다.

**세션 축**은 flow 단계를 어느 모델의 세션에서 도는가다.
설계 단계와 실행 단계를 다른 모델로 나눌 수 있고, 그 경계는 설계 문서 파일이다.

**디스패치 축**은 한 세션 안에서 띄우는 서브에이전트를 어느 모델로 돌리는가다.
조사원·리뷰어·구현자가 여기 든다.

두 축은 독립이다.
표준 모델 세션에서 최상위 모델 리뷰어를 띄울 수 있고 그 반대도 된다.

## Session axis: split design from execution

설계 문서는 자기완결 문서다.
`groundwork:writing-for-junior`(맥락 없는 주니어 독자 기준의 작성 규범) 규범이 맥락 없는 독자가 문서만으로 실행할 수 있게 쓰라고 요구하고 `groundwork:design-review`의 `junior-read` 렌즈가 그 기준으로 판정한다.
그 판정을 통과한 설계 문서는 세션 하나를 통째로 넘기는 핸드오프 단위가 된다.

그래서 다음 배정이 성립한다.

| 단계 | 티어 | 근거 |
|---|---|---|
| finding-unknowns · design-review · 승인 | 가장 유능한 모델 | 미확정을 찾아내고 사용자 의도를 읽는 일이라 판단이 곧 산출물이다 |
| executing-design · subagent-driven-development | 표준 모델 | 계약이 확정된 뒤의 실행이다. 분해와 구현에 판단이 들지만 방향은 이미 정해져 있다 |

**이 분할은 디스패치 경계가 아니라 세션 경계다.**
새 세션은 설계 문서 파일을 읽고 시작하므로 잃을 컨텍스트가 없고 따라서 복원할 것도 없다.
서브에이전트로 태스크마다 모델을 내리는 것과 여기가 갈린다.
그쪽은 쌓아 둔 컨텍스트를 버린 뒤 디스패치 프롬프트로 부분 복원하고 이쪽은 애초에 쌓인 것이 없다.

**성립 조건은 설계 문서의 자기완결성 하나다.**
검증되지 않은 설계 문서를 새 세션에 넘기면 그 세션은 물어볼 대상이 없는 채로 추측한다.
아래 표가 `groundwork:design-review`의 반환별로 분할 가능 여부를 정한다.

| 리뷰 반환 | 분할 |
|---|---|
| `통과` | 쓴다 |
| `조건부 통과` | 남은 발견이 `junior-read` 렌즈의 것이면 쓰지 않는다. 다른 렌즈의 것이면 그 발견을 새 세션에 함께 넘기고 쓴다 |
| `건너뜀` | 쓰지 않는다 |
| 로스터에서 `junior-read`가 빠짐 | 쓰지 않는다 |

`조건부 통과`를 두 갈래로 가르는 이유는 남은 발견이 무엇을 뜻하느냐가 렌즈마다 다르기 때문이다.
`junior-read`의 잔여는 맥락 없는 독자가 이 문서를 읽지 못한다는 뜻이고 새 세션이 정확히 그 독자다.
다른 렌즈의 잔여는 문서가 담은 결정에 관한 것이라 새 세션이 그 잔여를 알고 시작하면 된다.

분할을 쓰지 않기로 했으면 실행을 같은 세션에서 이어 간다.
설계 단계 세션이 그대로 실행으로 넘어가므로 문서에 없는 것을 자기 맥락에서 채울 수 있다.

**분해 해상도와 실행 티어는 서로 맞바꾸는 관계다.**
설계 문서가 계약이라 어떤 순서로 어느 파일을 건드릴지는 실행 스킬이 정한다.
그 분해에 판단이 들기 때문에 실행 티어를 싼 모델까지 내리지 않는다.
싼 모델로 내리려면 분해까지 미리 확정해 브리프에 담아야 하고, 그러면 그 확정을 누군가 더 비싼 모델로 해야 하므로 절약분이 앞단으로 옮겨 갈 뿐이다.
아래 「Turn count beats token price」와 같은 이유다.

## Dispatch axis: implementation and design tasks

**기계적 구현**(고립된 함수, 명확한 브리프, 파일 한둘): 싼 모델.
브리프에 쓸 코드가 그대로 들어 있어 옮겨 적기와 테스트만 남는 태스크가 여기다.

**통합·판단 태스크**(다중 파일 조율, 패턴 매칭, 디버깅): 표준 모델.

**아키텍처·설계 태스크**: 가장 유능한 모델.
브랜치 전체를 보는 최종 리뷰가 여기 속한다.

**fix 루프 상승**: 막힌 구현자보다 한 단계 유능한 모델로 올린다.

## Dispatch axis: code review tasks

diff의 크기·복잡도·위험에 맞춘다.
작고 기계적인 diff에 최상위 모델이 필요하지 않고 미묘한 동시성 변경에는 필요하다.
작은 수정 diff의 범위 한정 재리뷰는 싼 모델이나 표준 모델이면 된다.

## Dispatch axis: investigation tasks

`groundwork:finding-unknowns`의 블라인드 스팟·레퍼런스·스파이크와 `groundwork:dispatching-parallel-agents`의 영역별 조사는 표준 모델.
코드베이스를 훑고 산문으로 보고하는 일이라 싼 모델은 턴을 더 쓴다.
조사 대상이 아키텍처 판단으로 넘어가면 가장 유능한 모델로 올린다.

## Dispatch axis: document review lenses

`groundwork:design-review`가 띄우는 리뷰어의 티어다.
판정 기준은 렌즈가 하는 일의 성격이다.

- 문서에 적힌 것을 기준과 대조해 결손을 찾는 렌즈는 **표준 모델**.
- 문서에 적히지 않은 것을 추론해야 판정되는 렌즈는 **가장 유능한 모델**.

| 렌즈 | 티어 | 판정 성격 |
|---|---|---|
| `junior-read` | 표준 | 규범 축과 본문을 대조한다 |
| `completeness` | 표준 | 필수 항목의 결손을 찾는다. 수용 기준의 판정 가능성도 여기서 본다 |
| `coherence` | 표준 | 모호어·이중 해석과 절 사이 모순을 찾는다 |
| `crossref` | 표준 | 연관 산출물과 대조한다 |
| `facts` | 표준 | 주장과 근거를 대조한다 |
| `boundary` | 최상위 | 이 문서가 담을 범위의 경계와 요구되지 않은 것을 추론한다 |
| `intent` | 최상위 | 대화 맥락과 문서의 어긋남을 읽는다 |
| `experience` | 최상위 | 사용자가 겪을 것을 상상해 판정한다 |

리뷰어에 싼 모델을 쓰지 않는다.
아래 「Turn count beats token price」가 이유다.

## Cross-vendor dispatch

groundwork는 Claude Code와 Codex를 함께 덮는다.
두 실행 환경은 서로 다른 벤더의 모델 위에서 돌고, 그 사실 자체가 리뷰에서 쓸 수 있는 자원이다.

### What cross-vendor dispatch buys

**티어 절약이 아니라 판정의 독립성을 산다.**
같은 벤더의 모델을 다른 컨텍스트에 두면 컨텍스트는 갈리지만 학습에서 온 사각은 그대로 공유한다.
다른 벤더의 모델은 학습 데이터가 다르고 실패 양상이 달라서 그 사각을 덜 공유한다.
`groundwork:executing-design`이 리뷰만 격리하는 근거가 판정의 독립성인데, 벤더 교차는 그 독립성을 한 단계 더 올린다.

가격이 근거가 아니다.
다른 벤더의 중간 티어가 더 싸더라도 그것을 구현자로 쓰는 것은 교차 디스패치의 용도가 아니다.
구현을 벤더 밖으로 보내면 디스패치 경계가 다시 생기고 컨텍스트 재구성 비용이 돌아온다.

### Where it applies

교차 디스패치가 값어치를 하는 자리는 셋이다.

- **최상위 문서 리뷰 렌즈**: `boundary`·`intent`·`experience`.
  문서에 적히지 않은 것을 추론하는 축이라 판정자의 사전 성향이 결과를 가른다.
- **최종 코드 리뷰**: 브랜치 전체를 보는 판정.
  같은 벤더가 놓친 것을 다른 벤더가 잡는 자리다.
- **서브에이전트를 띄울 수 없는 실행 환경의 리뷰 게이트**: 격리 수단이 그것뿐일 때.

태스크 리뷰마다 교차로 돌리지 않는다.
왕복 비용이 붙고 독립성 이득은 최종 판정에서 가장 크다.

### The dispatch path is different

**서브에이전트의 모델 파라미터로는 다른 벤더에 갈 수 없다.**
그 파라미터는 실행 환경이 자기 벤더 안에서 제공하는 층만 받는다.
벤더 교차는 실행 환경이 제공하는 다른 경로를 쓴다.

| 실행 환경 | 자기 벤더 티어 | 벤더 교차 |
|---|---|---|
| Claude Code | 서브에이전트 디스패치 도구의 모델 파라미터 | 다른 벤더를 붙인 MCP 서버, 또는 해당 벤더의 CLI를 셸로 호출 |
| Codex | 그 실행 환경이 제공하는 서브에이전트 수단 | 같은 방식으로 다른 벤더를 붙인다 |

**경로가 없으면 교차 디스패치를 건너뛴다.**
다른 벤더를 부를 수단이 실행 환경에 없으면 같은 벤더 안의 격리로 돌아간다.
교차 디스패치는 독립성을 올리는 선택지이지 리뷰의 전제 조건이 아니다.
경로가 있는지는 실행 시점에 확인하고 없다는 이유로 리뷰를 건너뛰지 않는다.

**교차로 받은 판정도 같은 규율로 처리한다.**
다른 벤더가 냈다는 이유로 발견에 가중치를 더 주거나 덜 주지 않는다.
처리 규율은 `groundwork:receiving-code-review`(받은 리뷰 피드백을 검증하고 대응하는 규율)가 정본이다.

## Turn count beats token price

실시간과 컨텍스트 비용은 서브에이전트가 몇 턴을 쓰느냐로 늘어난다.
싼 모델은 여러 단계 작업에서 턴을 두세 배 쓰는 일이 잦아 총비용이 더 든다.

- 리뷰어와 산문 서술로 일하는 구현자는 표준 모델을 바닥으로 잡는다.
- 브리프에 쓸 코드가 그대로 들어 있으면 구현은 옮겨 적기와 테스트라 싼 모델을 쓴다.
- 단일 파일 기계적 수정도 싼 모델을 쓴다.

이 조항이 티어를 내리는 판단보다 우선한다.
싼 모델로 내렸는데 턴이 늘면 내린 것이 아니라 옮긴 것이다.
