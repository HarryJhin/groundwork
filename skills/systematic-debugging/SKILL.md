# systematic-debugging

**핵심 원칙**: 수정을 시도하기 전에 항상 근본 원인을 찾는다. 증상 수정은 실패다.

**이 절차를 글자 그대로 지키지 않는 것은 디버깅의 취지를 저버리는 것이다.**

## 철칙

```
근본 원인 조사 없이 수정하지 않는다
```

근본 원인 조사(아래 「절차」의 1단계)를 마치지 않았다면 수정을 제안할 수 없다.

## 적용 대상

모든 기술적 문제에 쓴다. 테스트 실패, 프로덕션 버그, 예상 밖 동작, 성능 문제, 빌드 실패, 통합 문제.

**특히 다음 상황에서 쓴다**:
- 시간 압박을 받을 때(급하면 추측이 달콤해진다)
- "빠른 수정 하나면 될 것" 같을 때
- 이미 여러 수정을 시도했을 때
- 앞선 수정이 듣지 않았을 때
- 문제를 온전히 이해하지 못했을 때

**다음 이유로 건너뛰지 않는다**:
- 문제가 단순해 보인다(단순한 버그에도 근본 원인이 있다)
- 급하다(서두르면 재작업이 확정된다)
- 지금 당장 고쳐야 한다(체계적인 쪽이 헤매는 것보다 빠르다)

## 절차

각 단계를 마쳐야 다음으로 간다.

### 1단계. 근본 원인 조사

**어떤 수정이든 시도하기 전에** 한다.

1. **에러 메시지를 정독한다**
   - 에러·경고를 건너뛰지 않는다
   - 거기에 정확한 해법이 들어 있는 경우가 많다
   - 스택 트레이스를 끝까지 읽는다
   - 라인 번호·파일 경로·에러 코드를 기록한다

2. **일관되게 재현한다**
   - 신뢰성 있게 유발할 수 있는가
   - 정확한 절차가 무엇인가
   - 매번 일어나는가
   - 재현되지 않으면 데이터를 더 모은다. 추측하지 않는다

3. **최근 변경을 확인한다**
   - 무엇이 바뀌어 이것을 일으켰나
   - git diff, 최근 커밋
   - 새 의존성, 설정 변경
   - 환경 차이

4. **다중 컴포넌트 시스템에서 증거를 모은다**

   시스템에 컴포넌트가 여럿이면(CI → 빌드 → 서명, API → 서비스 → DB) 수정을 제안하기 전에 진단 계측을 넣는다.

   ```
   각 컴포넌트 경계마다:
     - 컴포넌트에 들어가는 데이터를 로깅
     - 컴포넌트에서 나오는 데이터를 로깅
     - 환경·설정 전파를 확인
     - 각 층의 상태를 확인

   한 번 돌려 어디서 깨지는지 보여주는 증거를 모은다
   그 증거로 실패 컴포넌트를 특정한다
   그 컴포넌트만 파고든다
   ```

   이렇게 하면 어느 층이 실패하는지 드러난다. 예를 들어 비밀값은 워크플로까지 정상 전달됐고 워크플로에서 빌드로 넘어가는 경계에서 깨졌다.

5. **데이터 흐름을 추적한다**

   에러가 콜스택 깊은 곳에 있으면 역방향으로 추적한다. 상세 기법은 [root-cause-tracing.md](root-cause-tracing.md)에 있다.

   요약하면 이렇다. 나쁜 값이 어디서 비롯됐는가. 무엇이 나쁜 값으로 이것을 호출했는가. 출처를 찾을 때까지 위로 올라간다. 증상이 아니라 출처를 고친다.

### 2단계. 패턴 분석

1. **작동하는 예를 찾는다**: 같은 코드베이스에서 비슷한데 작동하는 코드를 찾는다
2. **레퍼런스와 대조한다**: 패턴을 구현 중이면 레퍼런스 구현을 **끝까지** 읽는다. 훑지 않는다
3. **차이를 식별한다**: 작동하는 것과 깨진 것의 차이를 아무리 작아도 전부 나열한다. "그게 문제일 리 없다"고 넘기지 않는다
4. **의존성을 이해한다**: 어떤 컴포넌트·설정·환경이 필요한가. 무엇을 전제하는가

### 3단계. 가설과 검증

1. **가설 하나를 세운다**: "Y 때문에 X가 근본 원인이라고 본다"를 명확히 적는다. 모호하지 않고 구체적으로
2. **최소로 검증한다**: 가설을 검증할 가장 작은 변경을 만든다. 한 번에 변수 하나. 여러 개를 동시에 고치지 않는다
3. **계속하기 전에 확인한다**: 됐으면 4단계로. 안 됐으면 **새 가설**을 세운다. 수정 위에 수정을 쌓지 않는다
4. **모를 때**: "X를 이해하지 못하겠다"고 말한다. 아는 척하지 않는다. 도움을 청하거나 더 조사한다

### 4단계. 구현

**증상이 아니라 근본 원인을 고친다.**

1. **실패 테스트 케이스를 만든다**
   - 가장 단순한 재현
   - 가능하면 자동화 테스트, 프레임워크가 없으면 일회성 스크립트
   - 고치기 전에 반드시 있어야 한다
   - 제대로 된 실패 테스트 작성은 `groundwork:test-driven-development`를 쓴다

2. **수정 하나를 구현한다**
   - 식별한 근본 원인을 해결한다
   - 한 번에 하나
   - "온 김에" 개선 금지
   - 리팩터링 끼워넣기 금지

3. **수정을 검증한다**
   - 테스트가 통과하는가
   - 다른 테스트가 깨지지 않았는가
   - 문제가 실제로 해소됐는가
   - 성공을 주장하기 전에 `groundwork:verification-before-completion`을 쓴다

4. **수정이 듣지 않으면**
   - 멈춘다
   - 센다. 수정을 몇 번 시도했는가
   - 3회 미만이면 1단계로 돌아가 새 정보로 재분석한다
   - **3회 이상이면 멈추고 아키텍처를 의심한다(4단계 5항)**
   - 아키텍처 논의 없이 4번째 수정을 시도하지 않는다

5. **수정 3회가 실패했으면 아키텍처를 의심한다**

   아키텍처 문제를 가리키는 패턴은 이렇다. 수정할 때마다 다른 곳에서 새 공유 상태·결합이 드러난다. 수정하려면 "대규모 리팩터링"이 필요하다. 수정이 다른 곳에 새 증상을 만든다.

   멈추고 근본을 의심한다. 이 패턴이 근본적으로 건전한가. 관성으로 붙들고 있는 것은 아닌가. 증상을 계속 고칠 것이 아니라 아키텍처를 리팩터해야 하는가.

   **더 수정하기 전에 사용자와 논의한다.**

   이것은 실패한 가설이 아니라 잘못된 아키텍처다.

## Red Flags. 멈추고 절차를 따른다

이런 생각이 들면 멈춘다.

- "일단 빠르게 고치고 나중에 조사하자"
- "X를 바꿔보고 되는지 보자"
- "여러 개 바꾸고 테스트 돌리자"
- "테스트는 건너뛰고 수동으로 확인하자"
- "아마 X일 테니 그것을 고치자"
- "완전히 이해하진 못했지만 이렇게 하면 될지도"
- "패턴은 X라지만 나는 다르게 고쳐 쓰겠다"
- "주요 문제는 다음과 같다"(조사 없이 수정 목록을 나열)
- 데이터 흐름을 추적하기 전에 해법을 제안한다
- **"한 번만 더 시도"(이미 2회 이상 시도했다)**
- **수정할 때마다 다른 곳에서 새 문제가 드러난다**

전부 같은 뜻이다. 멈추고 1단계로 돌아간다.

**3회 이상 실패했으면** 아키텍처를 의심한다(4단계 5항).

## 잘못 가고 있다는 사용자 신호

- "그게 안 일어나고 있나요?" → 확인 없이 가정했다
- "그걸 보여줄까요?" → 증거 수집을 넣었어야 했다
- "추측하지 마세요" → 이해 없이 수정을 제안하고 있다
- "깊이 생각해보세요" → 증상이 아니라 근본을 의심하라는 뜻이다
- "우리 막힌 건가요?"(답답함) → 접근이 듣지 않고 있다

이 신호가 보이면 멈추고 1단계로 돌아간다.

## 흔한 합리화

| 변명 | 실제 |
|---|---|
| "문제가 단순해서 절차가 필요 없다" | 단순한 문제에도 근본 원인이 있다. 단순한 버그에는 절차도 빠르다. |
| "긴급이라 절차 돌릴 시간이 없다" | 체계적 디버깅이 찍어보고 헤매는 것보다 빠르다. |
| "일단 이것부터 해보고 조사하자" | 첫 수정이 패턴을 정한다. 처음부터 제대로 한다. |
| "수정이 되는지 확인하고 테스트를 쓰겠다" | 검증 안 된 수정은 붙어 있지 않는다. 테스트가 먼저 증명한다. |
| "한꺼번에 고치면 시간이 절약된다" | 무엇이 들었는지 분리할 수 없다. 새 버그를 낳는다. |
| "레퍼런스가 길어서 패턴만 옮겨 쓰겠다" | 부분적 이해는 버그를 보장한다. 끝까지 읽는다. |
| "문제가 보인다, 고치겠다" | 증상을 보는 것과 근본 원인을 이해하는 것은 다르다. |
| "한 번만 더"(2회 이상 실패 후) | 3회 실패는 아키텍처 문제다. 또 고칠 것이 아니라 패턴을 의심한다. |

## 요약

| 단계 | 핵심 활동 | 성공 기준 |
|---|---|---|
| **1. 근본 원인** | 에러 정독, 재현, 변경 확인, 증거 수집 | 무엇이 왜 일어나는지 이해 |
| **2. 패턴** | 작동 예 탐색, 대조 | 차이 식별 |
| **3. 가설** | 이론 수립, 최소 검증 | 확인 또는 새 가설 |
| **4. 구현** | 테스트 작성, 수정, 검증 | 버그 해소, 테스트 통과 |

## "근본 원인이 없다"가 나올 때

체계적 조사 끝에 문제가 정말 환경적·타이밍 의존적·외부적이면 이렇게 한다. 절차를 마쳤음을 인정하고 조사한 것을 문서화하고 적절한 처리(재시도·타임아웃·에러 메시지)를 넣고 후속 조사를 위한 모니터링·로깅을 더한다.

다만 "근본 원인 없음" 사례의 대부분은 조사가 덜 끝난 것이다.
