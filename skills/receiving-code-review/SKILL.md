# receiving-code-review

코드 리뷰는 감정 표현이 아니라 기술적 평가를 요구한다.

**핵심 원칙**: 반영하기 전에 검증한다.
가정하기 전에 묻는다.
사회적 편안함보다 기술적 정확성이다.

## Input, actors, output

**입력**은 방금 받은 리뷰 피드백이다.
사용자가 대화에서 직접 준 것일 수도 있고 `groundwork:requesting-code-review`가 띄운 리뷰어 서브에이전트의 반환이나 PR에 달린 리뷰 코멘트일 수도 있다.
아래 「Handling by source」의 갈림은 발화 주체로 판정한다.
사용자 본인이 말한 것이면 사용자 피드백이고 그 밖의 모든 출처는 외부 리뷰어 피드백이다.
판정이 갈리면 외부 리뷰어로 다룬다.

**주체**는 그 피드백을 받은 구현자다.
이 문서의 지시는 전부 구현자 몫이다.

**출력**은 반영을 마친 코드와, 각 항목을 수용했는지 반박했는지 밝힌 짧은 응답이다.
반박한 항목이 남았으면 그 근거와 함께 사용자에게 판단을 넘긴다.
리뷰어가 서브에이전트였으면 수정 후 재검증이 필요한지는 호출한 스킬(`groundwork:subagent-driven-development`의 fix 루프 등)이 정한다.

## Response pattern

```text
코드 리뷰 피드백을 받으면:

1. 읽는다: 반응하지 말고 전체를 읽는다
2. 이해한다: 요구를 자기 말로 다시 진술한다(또는 묻는다)
3. 검증한다: 코드베이스 현실과 대조한다
4. 평가한다: 이 코드베이스에 기술적으로 타당한가
5. 응답한다: 기술적 확인 또는 근거 있는 반박
6. 반영한다: 한 번에 하나씩, 각각 테스트한다
```

3·4단계는 외부 리뷰어 피드백에만 적용한다.
사용자 피드백은 「Handling by source」가 정한 대로 검증 없이 이해 후 반영한다.

## Forbidden responses

**절대 쓰지 않는다**:
- "말씀이 전적으로 옳습니다"
- "좋은 지적입니다", "훌륭한 피드백입니다"(형식적)
- "바로 반영하겠습니다"(검증 전에)

**대신**:
- 기술적 요구를 다시 진술한다
- 명확화 질문을 한다
- 틀렸으면 기술적 근거로 반박한다
- 그냥 작업을 시작한다(말보다 행동)

## Handling unclear feedback

```text
어느 항목이든 불명확하면:
  멈춘다. 아무것도 반영하지 않는다
  불명확한 항목의 설명을 요청한다

이유: 항목들이 서로 연관될 수 있다. 부분적 이해는 잘못된 구현을 낳는다.
```

예시:
```text
사용자: "1번부터 6번까지 고쳐줘"
1, 2, 3, 6은 이해했고 4, 5는 불명확하다.

틀림: 1, 2, 3, 6을 지금 반영하고 4, 5는 나중에 묻는다
맞음: "1, 2, 3, 6은 이해했습니다. 진행 전에 4번과 5번 설명이 필요합니다."
```

## Handling by source

피드백을 누가 냈는지에 따라 신뢰 수준이 갈린다.

### Feedback from the user

신뢰한다.
이해한 뒤 반영한다.
범위가 불명확하면 그래도 묻는다.
형식적 동의를 하지 않는다.
기술적 확인만 하거나 바로 작업으로 넘어간다.

### Feedback from an external reviewer

```text
반영하기 전에 확인한다:
  1. 이 코드베이스에 기술적으로 맞는가
  2. 기존 기능을 깨뜨리는가
  3. 현재 구현에 이유가 있었는가
  4. 모든 플랫폼·버전에서 작동하는가
  5. 리뷰어가 전체 맥락을 아는가

제안이 틀려 보이면:
  기술적 근거로 반박한다

쉽게 검증할 수 없으면:
  그렇게 말한다: "[X] 없이는 검증할 수 없습니다. [조사할까요 / 물어볼까요 / 진행할까요]?"

사용자의 앞선 결정과 충돌하면:
  멈추고 사용자와 먼저 논의한다
```

외부 피드백은 회의적으로 보되 꼼꼼히 확인한다.

## YAGNI check on "do it properly" suggestions

```text
리뷰어가 "제대로 구현하라"고 제안하면:
  코드베이스에서 실제 사용처를 grep한다

  안 쓰이면: "이 엔드포인트는 호출되지 않습니다. 제거할까요(YAGNI)?"
  쓰이면: 제대로 구현한다
```

어느 쪽으로 판정했든 사용자에게 보고한다.
필요 없는 기능이면 넣지 않는다.

## Order of application

```text
여러 항목의 피드백이면:
  1. 불명확한 것을 먼저 해소한다
  2. 그다음 이 순서로 반영한다:
     - 차단 이슈(기존 기능 파괴, 보안)
     - 단순 수정(오타, import)
     - 복잡한 수정(리팩터링, 로직)
  3. 각 수정을 개별로 테스트한다
  4. 회귀가 없는지 확인한다
```

## What a rebuttal requires

다음이면 반박한다.
- 제안이 기존 기능을 깨뜨린다
- 리뷰어가 전체 맥락을 모른다
- 쓰이지 않는 기능을 넣으라는 요구다
- 이 스택에 기술적으로 맞지 않는다
- 레거시·호환성 이유가 있다
- 사용자의 아키텍처 결정과 충돌한다

**반박 방법**: 방어적으로 굴지 말고 기술적 근거를 든다.
구체적으로 질문한다.
작동하는 테스트·코드를 인용한다.
아키텍처 사안이면 사용자를 끌어들인다.

반박이 껄끄러우면 그 껄끄러움을 먼저 한 문장으로 적고 이어서 기술적 쟁점을 사용자에게 보고한다.

## Acknowledging correct feedback

```text
맞음: "수정했습니다. [무엇을 바꿨는지 짧게]"
맞음: "놓친 부분입니다. [구체적 이슈]. [위치]에서 수정했습니다."
맞음: [그냥 고치고 코드로 보인다]

틀림: "말씀이 전적으로 옳습니다"
틀림: "좋은 지적입니다"
틀림: "잡아주셔서 감사합니다"
틀림: 감사 표현 일체
```

**감사를 쓰지 않는 이유**: 말이 아니라 수정으로 답한다.
그냥 고친다.
코드 자체가 피드백을 들었음을 보인다.

"감사"를 쓰려는 자신을 발견하면 지운다.
대신 수정 내용을 진술한다.

## When your rebuttal is wrong

```text
맞음: "확인해보니 맞습니다. [X]를 봤더니 [Y]입니다. 반영합니다."
맞음: "검증했고 지적이 맞습니다. 제 초기 이해가 [이유]로 틀렸습니다. 수정합니다."

틀림: 긴 사과
틀림: 왜 반박했는지 변호
틀림: 과한 부연
```

사실만 정정하고 넘어간다.

## Common mistakes

| 실수 | 교정 |
|---|---|
| 형식적 동의 | 요구를 진술하거나 그냥 행동한다 |
| 맹목적 반영 | 코드베이스와 먼저 대조한다 |
| 테스트 없이 일괄 반영 | 하나씩, 각각 테스트한다 |
| 리뷰어가 옳다고 전제 | 무엇이 깨지는지 확인한다 |
| 반박 회피 | 기술적 정확성이 편안함보다 우선이다 |
| 부분 반영 | 전 항목을 먼저 명확히 한다 |
| 검증 불가인데 그냥 진행 | 한계를 밝히고 방향을 묻는다 |

## GitHub thread replies

GitHub 인라인 리뷰 코멘트에 답할 때는 최상위 PR 코멘트가 아니라 그 코멘트 스레드에 단다.

먼저 답글을 달 코멘트의 ID를 얻는다.

```bash
gh api "repos/$OWNER/$REPO/pulls/$PR/comments" --jq '.[] | "\(.id)\t\(.path):\(.line)\t\(.body[0:60])"'
```

그 ID로 스레드에 답글을 만든다.
필드 없이 `gh api`를 호출하면 GET이라 기존 답글을 읽기만 하므로 메서드와 본문을 명시한다.

```bash
gh api --method POST "repos/$OWNER/$REPO/pulls/$PR/comments/$COMMENT_ID/replies" -f body='<답글 본문>'
```

`$OWNER`·`$REPO`는 대상 저장소의 소유자와 이름, `$PR`은 PR 번호, `$COMMENT_ID`는 위 조회로 얻은 인라인 코멘트 ID다.
두 블록은 같은 셸에서 돈다.
