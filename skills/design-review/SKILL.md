# design-review

설계 문서를 쓴 저자가 같은 세션에서 한 번 self-review하고 판정한다.
별도 리뷰어를 띄우지 않고 리뷰 범위를 묻거나 라운드를 반복하지 않는다.

## Input, actor, output

리뷰 대상 설계 문서 경로를 호출자에게 받는다.
경로가 없으면 어느 문서를 볼지 묻고 임의로 고르지 않는다.

이 스킬을 로드한 에이전트가 `저자`이자 `리뷰어`다.
사용자 요청 원문과 역인터뷰 답변은 현재 세션의 원문을 쓴다.
원문이 없으면 도메인 권한을 판정할 수 없다는 사실을 잔여로 남긴다.

출력은 아래 둘 중 하나다.

| 상태 | 판정 |
|------|------|
| `통과` | 한 번의 self-review에서 발견한 설계 결함을 모두 처리했다 |
| `조건부 통과` | 사람만 정할 수 있거나 사실을 확인할 수 없어 처리하지 못한 설계 결함이 남았다 |

리뷰 상태와 중간 발견을 파일로 남기지 않는다.

## Review boundary

도메인 결정은 사용자에게 권한이 있다.
사용자 흐름·업무 의미·사용자에게 보이는 결과가 달라지는 선택은 요청 원문이나 역인터뷰 답변으로만 확정한다.
리포의 현재 구현·참조 구현·관행은 현재 상태의 증거이지 목표 도메인 정책의 근거가 아니다.

공개 인터페이스·영속 데이터·시스템 경계·주 실행 모델·호환성처럼 구현 뒤 되돌리기 비싼 선택은 설계가 소유한다.
파일·함수·내부 자료구조·헬퍼 배치·국소 알고리즘·작업 순서·테스트 파일처럼 같은 계약을 만족하는 선택은 구현이 소유한다.
구현 선택이 비어 있는 것은 발견이 아니다.

## One-pass criteria

문서 전문, 사용자 요청 원문, 역인터뷰 답변, 문서가 근거로 든 실물을 한 컨텍스트에서 대조한다.
아래 기준을 한 번에 적용한다.

### Intent and scope

- 요청의 목표가 「Scope」에 있고 요청하지 않은 기능이 들어오지 않았는가
- 「Non-goals」이 사용자가 원한 것을 배제하거나 저자가 임의로 정한 범위를 담지 않았는가
- 같은 요구를 서로 다르게 말하거나 함께 만족할 수 없는 계약이 없는가

### Domain authority and scenarios

- 「User flows and scenarios」의 정상·대안·실패·취소·재시도·재개 중 적용되는 경로가 있는가
- 각 경로에서 사용자가 관측하는 결과가 명확한가
- 각 도메인 결과를 확정한 사용자 발화를 지목할 수 있는가
- 현재 구현이나 참조 동작이 사용자 확인 없이 목표 동작으로 승격되지 않았는가

### Design boundary

- 도메인 계약을 구현에 넘기지 않았는가
- 공개 계약·영속 데이터·시스템 경계·호환성처럼 되돌리기 비싼 결정과 트레이드오프가 있는가
- 내부 구현 방법을 설계 결손처럼 확정하지 않았는가

### Facts and impact

- 현재 상태라고 쓴 사실이 리포·공식 문서·관측 결과와 맞는가
- 목표 상태와 현재 구현의 차이가 기존 데이터·공개 계약·하류 소비자에 미치는 영향이 「Compatibility and migration」에 있는가
- 현재 구현과 다르다는 이유만으로 사용자가 정한 목표 동작을 바꾸지 않았는가

### Acceptance

- 「Acceptance criteria」가 「Scope」와 「User flows and scenarios」의 관측 결과를 덮는가
- 각 기준의 참·거짓과 확인 방법이 갈리는가
- 보안·프라이버시·관측성·운영 부담 중 이 변경이 건드리는 제약이 빠지지 않았는가

## Process findings

모든 기준을 훑은 뒤 발견을 한 번에 처리한다.

- 사용자 발화나 확인된 사실이 이미 답을 주면 문서를 고친다.
- 도메인 결정의 사용자 근거가 없으면 추론하지 않고 `AskUserQuestion`으로 묻는다. 답을 문서에 반영해 같은 self-review 안에서 계속한다.
- 확인 가능한 현재 사실은 도구로 확인하고 확인하지 못하면 잔여로 남긴다.
- 구현이 소유한 선택은 발견에서 버리고 문서에 불필요하게 들어갔으면 덜어낸다.

사용자가 답하지 않거나 원문이 없어 도메인 권한을 확인할 수 없으면 잔여로 남긴다.
개정 때문에 리뷰를 다시 시작하지 않는다.
처리를 마친 문서를 기준으로 그 자리에서 최종 상태를 한 번 판정한다.

## Verdict

처리하지 못한 설계 결함이 없으면 `통과`다.
잔여가 있으면 각각의 위치, 잘못될 결과, 필요한 사용자 결정이나 사실 확인을 보고하고 `조건부 통과`다.

self-review 뒤 사용자 승인으로 넘어간다.
사용자 승인이 마지막 사용자 게이트이고 self-review가 그 승인을 대신하지 않는다.

## Red flags

| 생각 | 실제 |
|------|------|
| "독립 리뷰가 필요하니 에이전트를 띄우자" | 이 스킬은 저자의 self-review 한 번으로 끝난다 |
| "범위를 골라 달라고 하자" | 모든 기준을 한 번에 보고 범위 문항을 만들지 않는다 |
| "고쳤으니 한 라운드 더 돌자" | 개정 처리를 포함한 한 번의 판정이며 재리뷰가 없다 |
| "코드가 이렇게 동작하니 요구도 같을 것이다" | 현재 구현은 도메인 권한이 없다 |
| "구현 방법이 둘이니 설계가 모호하다" | 도메인·설계 계약이 같으면 구현자가 정한다 |
