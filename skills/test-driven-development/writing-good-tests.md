# Write good tests

**이 문서를 읽을 때**: 테스트를 쓰거나 고칠 때, 목을 추가할 때, 테스트용 정리·헬퍼 메서드를 추가할 때.

## The two principles that govern tests

테스트는 특정한 파손을 잡으려고 존재한다.
두 원칙이 나머지 전부를 지배한다.

```text
1. 모든 테스트는 자기가 잡는 파손을 이름 붙인다
2. 모든 테스트는 진짜를 돌린다
```

엄격한 TDD가 둘을 자연히 낳는다.
먼저 쓰고 실제 코드를 상대로 실패를 목격한 테스트는 이미 실패할 수 있음을 증명했고 실제 의존이 느리거나 외부임이 드러날 때만 목을 얻는다.

## Name the breakage

테스트 본문을 쓰기 전에 답한다.
**어떤 프로덕션 변경이 이 테스트를 실패시켜야 하는가.**
**그리고 그 변경은 버그인가 결정인가.**
테스트는 잘못된 분기, 빠진 부작용, 잘못된 인자, 경계 조건, 깨진 계약을 잡아서 존재 이유를 얻는다.

**기대값을 독립으로 유도한다.**
리터럴과 손으로 확인한 픽스처를 쓴다.
리터럴 `want` 값을 쓰는 테이블 주도 테스트가 선호하는 형태다.
검사 대상 코드나 그 헬퍼가 계산한 기대값은 그 코드가 무엇을 하든 통과한다.

```typescript
// 거울 단언: 같은 빌더가 양쪽을 계산한다. 항상 참이다
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// 손으로 유도한 리터럴
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**변경 탐지기를 만들지 않는다.**
의도적 결정만이 테스트를 실패시킬 수 있으면(상수의 값, 정확한 메시지 문구, 비공개 구조) 그 테스트는 재설계 때 울리고 버그에는 잠든다.
결정에 의존하는 동작을 검사한다.
`expect(MAX_RETRIES).toBe(5)`가 아니라 "실패하는 호출이 5번 재시도되고 6번째 시도는 일어나지 않는다"이다.

**텍스트가 아니라 동작이다.**
스크립트·스킬·설정이 특정 줄을 포함한다고 단언하는 것은 출처가 출처임만 증명한다.
스크립트는 통제된 입력으로 돌려 출력·부작용·종료 코드를 단언한다.
에이전트에 지시하는 문서는 그 문서를 소비하는 에이전트의 행동으로 검사한다(`groundwork:writing-skills`).
사람이 읽는 산문은 테스트를 얻지 않는다.

**프레임워크가 아니라 네 코드다.**
네 코드가 경계에서 맺는 계약을 검사한다.
네가 등록한 라우트, 네가 내보내는 쿼리, 네가 만드는 페이로드다.
상류의 동작 원리는 그 관리자들이 쓸 테스트다(고전적 사례: 네 라우터가 등록된 핸들러를 호출하는지 단언하는 것은 프레임워크의 테스트이지 네 것이 아니다).
상류 동작이 정말로 놀라웠다면 그 전제를 이름 붙인 좁은 특성화 테스트 하나를 쓴다.
같은 경계가 네 코드 안에도 적용된다.
생성자·게터·상수·단순 전달은 검증·정규화·기본값·유도·강제를 하거나 부작용을 일으킬 때만 테스트를 얻는다.
그렇지 않으면 그것에 의존하는 첫 소비자 가시 결과를 단언한다.

### Assertion-target gate function

```text
테스트 본문을 쓰기 전에:
  이 테스트를 실패시킬 프로덕션 변경에 이름을 붙인다.

  이름 붙일 수 없음        → 관찰 가능한 동작을 중심으로 재설계한다
  "소스 텍스트가 바뀜"      → 산출물을 돌려 그 효과를 단언한다
  의도적 결정만            → 변경 탐지기다. 그 결정에 의존하는 동작을 검사한다

  기대값이 검사 대상 코드 없이 유도됐는지 확인한다.
  그 코드의 로직이나 헬퍼를 재사용했다면:
    리터럴이나 손으로 확인한 픽스처로 바꾼다
```

## Run the real thing

**목은 단언을 얻지 못한다.**
목을 단언하면 목이 있을 때 통과하고 없을 때 실패한다.
컴포넌트에 관해서는 아무것도 말해 주지 않는다.
실제 컴포넌트의 동작을 단언한다.
확인하려는 것이 목이라면 목을 없애거나 그 단언을 지운다.

```typescript
// 실제 동작
expect(screen.getByRole('navigation')).toBeInTheDocument();

// 목의 존재
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

사용자의 교정: "우리가 목의 동작을 테스트하고 있나요?"

**올바른 층에서 목을 만든다.**
실제 메서드의 부작용을 전부 배운 뒤에 대체한다.
느리거나 외부인 연산을 목으로 만들고 테스트가 의존하는 것은 실제로 남긴다.
확신이 없으면 실제 구현을 상대로 먼저 테스트를 돌려 무엇이 실제로 일어나야 하는지 관찰한다.

```typescript
// 이 목이 중복 탐지가 읽는 설정 쓰기를 삼킨다
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// 느린 서버 기동만 목으로. 설정 쓰기는 실제로 남는다
vi.mock('MCPServerManager');
```

**대역을 구체적으로 만든다.**
인자·호출 횟수·순서가 계약의 일부면 그것을 단언한다.
무엇이든 받는 가짜는 아무것도 검증하지 않는다.
분기마다(성공·에러·비정상) 자기 픽스처나 스파이를 준다.
그래야 잘못된 분기가 기대를 만족시키지 못한다.

**실제 데이터를 온전히 반영한다.**
현실에 존재하는 완전한 구조를 목으로 만든다.
문서화된 모든 필드이지 테스트가 읽는 것만이 아니다.
부분 목은 하류 코드가 생략된 필드를 읽을 때 조용히 실패한다.
테스트는 통과하는데 통합이 깨진다.

**프로덕션 클래스는 프로덕션 메서드만 지닌다.**
테스트만 필요로 하는 정리는 테스트 유틸리티에 둔다.
프로덕션 클래스의 `destroy()`가 아니다.
물어본다.
이 메서드가 테스트에서만 호출되는가.
이 클래스가 이 자원의 수명주기를 소유하는가.
답이 틀리면 테스트 유틸리티로 간다.

**복잡한 목보다 실제 컴포넌트를 택한다.**
목 셋업이 테스트 로직보다 커지거나 목이 실제 컴포넌트에 있는 메서드를 빠뜨리거나 목이 바뀔 때 테스트가 깨지면 실제 컴포넌트를 쓰는 통합 테스트로 바꾼다.
사용자의 질문: "여기 목이 꼭 필요한가요?"

### Mock-addition gate function

```text
목이나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열한다. 테스트가 의존하는 것은 실제로 남기고
  그 아래의 느리거나 외부인 층을 목으로 만든다.

  목 응답이 완전한 실제 구조를 반영한다.

  테스트에서만 호출되는 메서드는 프로덕션이 아니라 테스트 유틸리티에 둔다.

  목 자체를 단언하려는 참인가?
    목을 걷어내거나 그 단언을 지운다
```

## Tests ship with the implementation

TDD 사이클(실패 테스트, 최소 구현, 리팩터)이 "완료"의 뜻이다.
그 동작에 필요한 테스트만 낸다.
사소한 코드와 사람이 읽는 산문은 테스트를 얻지 않고 절차를 만족시키려 쓴 테스트는 유지보수 비용을 영원히 남긴다.

## Mutation check

마치기 전에 프로덕션 코드를 머릿속으로 변이시킨다.
현실적인 변이마다 최소 테스트 하나가 실패해야 한다.

- 잘못된 상수나 인자
- 잘못된 분기 처리
- 빠진 상태 변경이나 부작용
- 빈 값이나 기본값 반환
- 0·빈 값·nil·비인가·비정상 입력에 대한 검증 누락

아무것도 잡지 못하는 변이는 그 동작이 보호받지 않거나 그 테스트가 항진명제임을 표시한다.

## Quick reference

| 이럴 때 | 이렇게 한다 |
|---|---|
| 테스트를 쓴다 | 잡는 파손에 이름을 붙인다. 결정이 아니라 버그다 |
| 기대값을 만든다 | 손으로 유도한다. 검사 대상 코드로는 절대 만들지 않는다 |
| 스크립트나 문서를 검사한다 | 돌리거나 소비자를 압박한다. 텍스트를 grep하지 않는다 |
| 의존성 테스트에 손이 간다 | 네 경계 계약을 검사한다. 의존성의 문서화된 동작 원리가 아니다 |
| 목으로 만든 요소를 단언하려 한다 | 실제 컴포넌트를 검사하거나 목을 걷어낸다 |
| 메서드를 목으로 만들려 한다 | 부작용을 배운다. 느리거나 외부인 층을 목으로 만든다 |
| 목 응답을 만든다 | 실제 구조를 온전히 반영한다 |
| 테스트만 쓰는 정리가 필요하다 | 테스트 유틸리티에 넣는다 |
| 목 셋업이 부푼다 | 실제 컴포넌트를 쓰는 통합 테스트로 바꾼다 |
| 테스트 파일을 마친다 | 변이 점검을 돌린다 |

## Warning signs

- 셋업과 단언이 같은 객체를 공유해 동등성이 보장된다
- 테스트가 패닉·크래시·셀렉터 부재로만 실패할 수 있다
- 의도적 변경마다 실패하고 우연한 파손에는 절대 실패하지 않는다
- 기대값이 루프·빌더·헬퍼 뒤에 숨어 있다
- 소스 텍스트를 grep하거나 제거된 심볼이 제거된 채로 있는지 단언한다
- 프레임워크만 남아도 그 테스트가 여전히 의미를 지닌다
- 커버리지를 위해 존재하고 어떤 부작용·결과도 확인하지 않는다
- 단언이 `*-mock` 테스트 ID를 확인하거나 목을 없애면 실패한다
- 메서드가 테스트 파일에서만 호출된다
- 목 셋업이 테스트의 절반을 넘거나 그 목이 왜 필요한지 설명할 수 없다
- "혹시 모르니" 목을 만든다
