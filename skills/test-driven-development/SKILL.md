# test-driven-development

테스트를 먼저 쓴다.
실패를 확인한다.
통과시킬 최소 코드를 쓴다.

**핵심 원칙**: 테스트가 실패하는 것을 보지 않았다면 그 테스트가 옳은 것을 검사하는지 모른다.

**규칙을 글자 그대로 지키지 않는 것은 규칙의 취지를 저버리는 것이다.**

## 적용 대상

**항상**: 새 기능, 버그 수정, 리팩터링, 동작 변경.

**예외(사용자에게 묻는다)**: 버리는 프로토타입, 코드 생성기가 출력한 코드(스키마·클라이언트 스텁 등), 설정 파일. 네가 직접 쓰는 코드는 예외가 아니다.

"이번만 TDD를 건너뛰자"는 생각이 들면 멈춘다.
그것이 합리화다.

**경로 기준**: 이 문서의 셸 블록에 나오는 테스트 파일 경로는 대상 프로젝트의 repo 루트 기준이고 커맨드는 그 루트에서 돈다.

**테스트 러너**: 아래 블록은 Node와 jest를 예시로 쓴다.
대상 프로젝트의 테스트 커맨드로 바꿔 실행한다.

**출력**: 이 스킬이 남기는 것은 테스트와 그것을 통과시키는 구현이다.
완료를 주장하기 전에 `groundwork:verification-before-completion`으로 넘긴다.

## 철칙

```
실패하는 테스트 없이 프로덕션 코드를 쓰지 않는다
```

테스트보다 코드를 먼저 썼다면 지운다.
처음부터 다시 한다.

예외는 없다.
먼저 쓴 그 코드를 이렇게 다룬다.

- "참고용"으로 남기지 않는다
- 그 코드에 맞춰 테스트를 짜 맞추지 않는다
- 쳐다보지 않는다
- 지운다는 것은 지운다는 뜻이다

테스트만 보고 구현을 처음부터 다시 쓴다.

## RED-GREEN-REFACTOR

### RED. 실패하는 테스트를 쓴다

무엇이 일어나야 하는지 보여주는 최소 테스트 하나를 쓴다.

좋은 예:
```typescript
test('retries failed operations 3 times', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```
이름이 명확하고 실제 동작을 검사하고 한 가지만 본다.

나쁜 예:
```typescript
test('retry works', async () => {
  const mock = jest.fn()
    .mockRejectedValueOnce(new Error())
    .mockRejectedValueOnce(new Error())
    .mockResolvedValueOnce('success');
  await retryOperation(mock);
  expect(mock).toHaveBeenCalledTimes(3);
});
```
이름이 모호하고 코드가 아니라 목(mock)을 검사한다.

요건은 다음과 같다.
동작 하나, 명확한 이름, 실제 코드(목 객체는 불가피할 때만).

### RED 확인. 실패를 목격한다

**필수다.**
**건너뛰지 않는다.**

```bash
npm test path/to/test.test.ts
```

확인할 것:
- 테스트가 실패한다(에러가 아니라 실패다)
- 실패 메시지가 예상한 것이다
- 기능이 없어서 실패한다(오타 때문이 아니다)

**테스트가 통과하면?**
이미 있는 동작을 검사하고 있다.
테스트를 고친다.

**테스트가 에러를 내면?**
에러를 고치고 올바르게 실패할 때까지 다시 돌린다.

### GREEN. 최소 코드

테스트를 통과시킬 가장 단순한 코드를 쓴다.

좋은 예:
```typescript
async function retryOperation<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try {
      return await fn();
    } catch (e) {
      if (i === 2) throw e;
    }
  }
  throw new Error('unreachable');
}
```
통과에 딱 필요한 만큼이다.

나쁜 예:
```typescript
async function retryOperation<T>(
  fn: () => Promise<T>,
  options?: {
    maxRetries?: number;
    backoff?: 'linear' | 'exponential';
    onRetry?: (attempt: number) => void;
  }
): Promise<T> {
  // YAGNI
}
```
과설계다.

기능을 더하거나 다른 코드를 리팩터하거나 테스트 너머로 "개선"하지 않는다.

### GREEN 확인. 통과를 목격한다

**필수다.**

```bash
npm test path/to/test.test.ts
```

확인할 것:
- 테스트가 통과한다
- 다른 테스트도 여전히 통과한다
- 출력이 깨끗하다(에러·경고 없음)

**테스트가 실패하면?**
테스트가 아니라 코드를 고친다.

**다른 테스트가 깨지면?**
지금 고친다.

### REFACTOR. 정리한다

green 이후에만 한다.
중복 제거, 이름 개선, 헬퍼 추출.

테스트를 green으로 유지한다.
동작을 더하지 않는다.

### 반복

다음 기능의 다음 실패 테스트로 간다.

## 좋은 테스트

| 성질 | 좋음 | 나쁨 |
|---|---|---|
| **최소** | 한 가지만. 이름에 "and"가 들어가면 쪼갠다 | `test('validates email and domain and whitespace')` |
| **명확** | 이름이 동작을 서술한다 | `test('test1')` |
| **의도를 드러냄** | 원하는 API를 보여준다 | 코드가 무엇을 해야 하는지 가린다 |

테스트를 쓰거나 고칠 때는 [writing-good-tests.md](writing-good-tests.md)를 읽는다.
테스트를 정직하게 유지하는 규칙이 거기 있다.

## 흔한 합리화

| 변명 | 실제 |
|---|---|
| "너무 단순해서 테스트할 게 없다" | 단순한 코드도 깨진다. 테스트는 30초 걸린다. |
| "나중에 테스트하겠다" | 나중에 쓴 테스트는 즉시 통과하고 그것은 아무것도 증명하지 않는다. 엉뚱한 것을 검사하거나 동작이 아니라 구현을 검사하거나 잊은 엣지케이스를 놓친다. 실패를 목격한 적이 없으니 그 테스트가 버그를 잡을 수 있다는 증명이 없다. 테스트 우선이 그 실패를 강제한다. |
| "나중 테스트도 정신은 같다" | 나중 테스트는 "이 코드가 무엇을 하는가"에 답하고 먼저 쓴 테스트는 "이 코드가 무엇을 해야 하는가"에 답한다. 이미 쓴 코드가 나중 테스트를 편향시킨다. 이미 떠오르는 경우만 검증하고 테스트를 먼저 썼다면 발견했을 경우는 놓친다. |
| "이미 수동으로 테스트했다" | 수동 테스트는 임시변통이다. 무엇을 덮었는지 기록이 없고 코드가 바뀔 때 다시 돌릴 방법이 없고 압박 속에서 빠뜨리기 쉽다. "해보니 되던데"는 포괄적이지 않다. |
| "몇 시간 작업을 지우는 건 낭비다" | 매몰비용 오류다. 그 시간은 어느 쪽이든 이미 썼다. 실제 선택은 TDD로 다시 쓰기(높은 확신)와 그대로 두고 테스트를 덧붙이기(낮은 확신, 버그 잔존) 사이다. 믿을 수 없는 코드를 지니는 것이 낭비다. |
| "참고용으로 두고 테스트를 먼저 쓰겠다" | 그 코드에 맞춰 테스트를 짜 맞추게 된다. 그것이 나중 테스트다. 지운다는 것은 지운다는 뜻이다. |
| "먼저 탐색이 필요하다" | 좋다. 탐색은 버리고 TDD로 시작한다. |
| "이건 테스트하기 어려운 코드라 TDD가 안 맞는다" | 테스트의 말을 듣는다. 테스트하기 어려우면 쓰기도 어렵다. 어려움은 면제 사유가 아니라 설계 신호다. |
| "TDD는 속도를 늦춘다" | TDD가 실용적인 길이다. 커밋 전에 버그를 잡고 회귀를 막고 두려움 없이 리팩터하게 한다. "실용적" 지름길은 프로덕션에서 디버깅하는 결과를 낳는다. |
| "기존 코드에 테스트가 없다" | 그 코드를 개선하는 중이다. 기존 코드에도 테스트를 더한다. |

## Red Flags. 멈추고 다시 시작한다

- 테스트보다 코드가 먼저다
- 구현 후에 쓴 테스트
- 테스트가 즉시 통과한다
- 테스트가 왜 실패했는지 설명할 수 없다
- 테스트를 "나중에" 추가한다
- "이번만"이라는 합리화
- "이미 수동으로 확인했다"
- "취지가 중요하지 형식이 중요한 게 아니다"
- "참고용으로 두겠다", "기존 코드에 맞춰 테스트를 짜 맞추겠다"
- "몇 시간 썼는데 지우는 건 아깝다"
- "TDD는 교조적이고 나는 실용적이다"
- "이건 다른 경우다"

전부 같은 뜻이다.
코드를 지우고 TDD로 다시 시작한다.

## 예시: 버그 수정

**버그**: 빈 이메일이 통과한다

**RED**
```typescript
test('rejects empty email', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('Email required');
});
```

**RED 확인**
```bash
$ npm test
FAIL: expected 'Email required', got undefined
```

**GREEN**
```typescript
function submitForm(data: FormData) {
  if (!data.email?.trim()) {
    return { error: 'Email required' };
  }
  // ...
}
```

**GREEN 확인**
```bash
$ npm test
PASS
```

**REFACTOR**: 필드가 여럿이면 검증을 추출한다.

## 완료 전 체크리스트

- [ ] 새 함수·메서드마다 테스트가 있다
- [ ] 구현 전에 각 테스트의 실패를 목격했다
- [ ] 각 테스트가 예상한 이유로 실패했다(오타가 아니라 기능 부재)
- [ ] 통과시킬 최소 코드를 썼다
- [ ] 전 테스트가 통과한다
- [ ] 출력이 깨끗하다(에러·경고 없음)
- [ ] 테스트가 실제 코드를 쓴다(목 객체는 불가피할 때만)
- [ ] 엣지케이스와 에러 경로를 덮었다

전부 체크할 수 없으면 TDD를 건너뛴 것이다.
다시 시작한다.

## 막혔을 때

| 문제 | 해법 |
|---|---|
| 어떻게 테스트할지 모른다 | 원하는 API를 쓴다. 단언부터 쓴다. 사용자에게 묻는다. |
| 테스트가 너무 복잡하다 | 설계가 너무 복잡하다. 인터페이스를 단순화한다. |
| 전부 목 객체로 만들어야 한다 | 코드가 너무 결합돼 있다. 의존성 주입을 쓴다. |
| 테스트 셋업이 거대하다 | 헬퍼를 추출한다. 그래도 복잡하면 설계를 단순화한다. |

## 디버깅 연계

버그를 찾았으면 그것을 재현하는 실패 테스트를 쓴다.
TDD 사이클을 따른다.
그 테스트가 수정을 증명하고 회귀를 막는다.
근본 원인 조사는 `groundwork:systematic-debugging`이 정본이다.

테스트 없이 버그를 고치지 않는다.

## 최종 규칙

```
프로덕션 코드 → 테스트가 존재하고 먼저 실패했다
그 외 → TDD가 아니다
```

사용자의 허락 없이는 예외가 없다.
